- Beta baseline: the 1.7.0 cycle started when beta was restored to the 1.6.0

  verified the restoration is exact: a byte comparison of the full
  `librecoach/` tree at beta `933d7c4` against prod `bde25fb` shows identity
  except `config.yaml` (only the `image:` line differs, as designed) and
  `Dockerfile` (beta `933d7c4` already carries the authenticated Node-RED
  fetch that prod applied later in `380f206`; the two are the same change —
  current prod and beta Dockerfiles are byte-identical, confirmed by the
  mirror dry run showing a timestamp-only difference).
- Prod baseline: `bde25fb` is the 1.6.0 release commit; prod also carries two
  post-release commits in scope for this audit, `380f206` (fix build:
  authenticated Node-RED fetch) and `161ec54` (CI: fail the build when prod
  `librecoach/` drifts from beta), plus merge `15a3b79`.
- Node-RED baseline: unambiguous. Prod `main` commits the exact revision it
  builds into `librecoach/node-red.ref`; at `bde25fb` (and at prod HEAD) that
  file contains `4109cfda3d8bb683899911f4fc5582d20847cb17`
  ("docs(wiring): carry the shade publisher's contract into the map",
  2026-08-21, one commit after the `chore: v1.6.0` node-red tag commit
  `e4db24c`). The Dockerfile fetches exactly this ref, so the 1.6.0 image
  bundled exactly this tree. No date-guessing needed. `beta-notes/beta_sync_plan.md`
  states the same ref.
- Node-RED head: beta `node-red.ref` at `8d283af` pins
  `23760597b5a1fe66a24e668bd71842de65ba30fb`, which is local main HEAD and —
  confirmed live with `git ls-remote` — GitHub `origin/main`, so the
  build-time fetch will succeed. All four in-window ref pins
  (`ad9912e`, `d179910`, `c83307c`, `814991d`, `2376059`) form a strictly
  linear ancestor chain, so no beta image ever shipped a node-red revision
  that is not an ancestor of the final one.

Method: commit-by-commit review with real diffs (`rtk proxy git diff` /

only artifact.

## Verdict

**Ship — with one code decision, two documentation gaps, and one pre-existing
link bug to decide on before the release commit; no code blockers.**

The code surface is sound. Every commit in the window was accounted for
(verified / suspect / superseded below); every fix-of-a-fix chain in the
window genuinely closes the defect it targets; the shipped `artifact/flows.json`
is byte-consistent with all 171 split-source function files at the pinned
revision; all four test suites pass (node-red 697, BLE bridge 43, vehicle
bridge 6, orchestrator state shell test); the cross-repo contracts (MQTT
topics, export paths, ports, credential placeholders, node-red ref) agree;
and the config surface has zero option/schema changes, so the mirror
hand-port list is empty.

No confirmed defect makes the shipping payload wrong in the happy path. The
items to close before the release commit:

1. **One deliberate decision — Finding F4 (medium):** digital-input entities
   go stale-ON and remain "available" when their TM-102 module disappears
   (no per-module analog of the ATS watchdog that this same window built).
   It is new-surface degradation, not a 1.6.0 regression, and the happy path
   is correct — but it is the one spot in the release that violates the
   repo's own "unavailable is correct when a device is offline" rule. Either
   land a small per-node watchdog (modeled on `ats_watchdog.js`) before the
   release commit, or consciously ship it and record the limitation in the
   1.7.0 notes. Related low: F5 (dead-module poll never backs off).
2. **The 1.7.0 CHANGELOG omits the Aug 27 Node-RED export/import fixes**
   (export download links on configurable HA ports, import page
   completion/watchdog, retained RV details in exports) — Finding F3. A
   minute of edits.
3. **`releases/1-7-0.md` (community announcement post) does not exist yet,
   and `librecoach-site` has 6 unpushed held commits plus one uncommitted
   doc edit** that the sync plan requires to be reviewed and pushed
   alongside the release — Finding F7.
4. **One pre-existing user-visible bug to decide on while the release is
   open — Finding P7:** the import notification's "Open Import Page" link
   404s everywhere (dead `/endpoint/` path segment + hardcoded
   `homeassistant.local:1880`). Not a 1.7.0 regression — it predates the
   window — but the release notes advertise the sibling export-link fix, so
   a one-line fix (drop the segment) rides cheaply in this release.

Everything else listed under Findings is a low-severity edge case (F1, F2 on
the beta orchestrator; F5, F6, F8 on node-red), a latent (currently-passing)
CI quirk (P1), or documented behavior (L1, P2, P3, S1, F9).

## Findings

### Confirmed

**F1 — Stale "pending install" marker is never expired; it can suppress the takeover prompt (low, suspected-becomes-real under a specific sequence).**
Repo: `ha-addons-beta`. `librecoach/run.sh:25` (file), `run.sh:528` (`mark_nodered_install_pending` writes `started_at`), `run.sh:513-526` (`classify_nodered_install_state`), `run.sh:1230`-area (`resume` disposition).
`started_at` is written to the pending marker but **never read** — there is no staleness check. The `resume` disposition (installed=true, not managed, pending=true) skips the takeover permission check entirely (`NODERED_ALREADY_INSTALLED` stays false) and proceeds to configure the add-on, which writes `credential_secret` + `init_commands` and does `del(.users)` on the Node-RED options.
Failure scenario: LibreCoach installs Node-RED; the process is killed in the (narrow) window between install completion and `mark_nodered_managed` (which clears the marker); the marker persists in `/data`. Much later, the user uninstalls and reinstalls Node-RED for their own purposes, adds their own auth/flows, and restarts LibreCoach → it classifies the user's fresh installation as "its own interrupted install" and adopts/overwrites it without the "Allow Node-RED Overwrite" prompt.
Why low: the window is a crash between two adjacent steps, plus a full user uninstall/reinstall of Node-RED in between. 1.6.0 has no pending marker at all, so this is new-surface, not a regression.
Confirmed by reading the state machine end-to-end; `started_at` unused (grep of `run.sh`). Suggested fix (not applied, per read-only scope): treat a pending marker older than e.g. 24h as stale and fall through to the `preexisting` path.

**F2 — `nodered_is_unconfigured` ignores the Node-RED `users` (auth) option (low, suspected).**
Repo: `ha-addons-beta`. `librecoach/run.sh:497-511`.
The adoption check requires state ≠ started, no `credential_secret`, no `init_commands` — but not that `.data.options.users` is empty. A Node-RED the user configured *only* with authentication (set users/password, never started, no flows) would be judged "unconfigured" and adopted; the subsequent options write does `del(.users)`, silently removing the user's auth configuration.
Why low: requires auth configured + never started + no init commands. The `started` check catches the common case (auth is configured from a running instance). Same class as F1: the "nothing to protect" judgment is slightly narrower than it should be.
Confirmed by reading the function against the options write at `run.sh:1385`-area. Suggested fix: also require `.data.options.users // []` to be empty.

**F3 — 1.7.0 CHANGELOG omits the Aug 27 export/import fixes (medium, docs).**
Repo: `ha-addons-beta` `librecoach/CHANGELOG.md`; the work is in `librecoach-node-red` `66eaaef`, `8396638`, `9227e88`, `814991d`, `2376059`.
The changelog's 1.7.0 entry was frozen at beta.1 (Aug 26); the later prepare commits bumped version/ref only and never added entries for: export download links now work on any Home Assistant host/port (relative `/local/...` links); configuration import now answers the browser page even when some entity-registry updates never report back (with the watchdog race closed in `2376059`); and configuration exports now retain RV details. All three are user-visible fixes of the export/import feature, and `beta_sync_plan.md` explicitly requires the changelog to cover user-facing fixes across the whole node-red OLD..NEW range.
Confirmed: final CHANGELOG text vs. the five commits' subjects and code.

**F4 — Digital-input entities go stale-ON and stay "available" when their module disappears (medium, high confidence — new behavior in this window).**
Repo: `librecoach-node-red`. `src/tabs/status-routing/status_digital_input.js:184-196`; poll suppression stamp at `src/tabs/config/decode_rvc_can.js:375`; no per-module watchdog exists (ATS has `ats_watchdog.js`; nothing equivalent covers `DIGITAL_INPUT_STATUS`).
The new digital-input binary sensors' availability tracks only `librecoach/nodered/status` + `can/status`. States are published retained, and nothing marks a module's inputs unavailable when the module stops transmitting.
Failure scenario: the generator-run signal on a TM102A input is ON (retained); the module loses power or the dash is powered down permanently; `binary_sensor.<input>` keeps showing ON as available indefinitely — while ATS entities on the same bus correctly flip unavailable after 10 s. This is the one spot in the new surface where the repo rule "unavailable is correct when a device is offline" is not honored. A TM102 watchdog modeled on `ats_watchdog` (per-node frame-gap → not-available) would close it.
Confirmed by reading the publisher's discovery/availability construction at HEAD and by absence (no per-instance availability topic, no watchdog tick for this DGN). This is the strongest candidate for a pre-release follow-up decision: it ships the intended happy path, but the offline path degrades to stale values.

**F5 — `poll_digital_input` polls a dead/removed TM-102 forever, no backoff (low, high confidence).**
Repo: `librecoach-node-red`. `src/tabs/config/poll_digital_input.js:33-47`; driving inject `30103737b59a3c8a` repeats every 20 s (`config.yaml:380`).
The only gate is `digital_input_last_seen_<node>` freshness; a module that never answers never refreshes it, so the addressed status request goes out every 20 s indefinitely after a module is unmounted or fails.
Failure scenario: owner removes a TM102A; its record stays in file-backed `rvcProductId`; LibreCoach sends ~3 pointless frames/min to a dead address forever. Negligible bus load, but inconsistent with the sibling pollers' own convention in the same window (`poll_product_id.js`, `poll_tm102_input_config.js` both use 3-attempts/6-h-rest — `85c0ba8`/`492d31f`).

- `test/digital-input-status-decode.test.js:42-43` comment still claims the *publisher* registers nodes for PRODUCT_ID (that moved to `decode_rvc_can.js` in `a6ce3a7`).

**F7 — Release-day artifacts incomplete (info, release hygiene).**
`releases/1-7-0.md` does not exist (the pre-release checklist requires it before release approval). `librecoach-site` main is 6 commits ahead of origin (the held 1.7.0 docs: configurable HA web ports, share-folder backups, digital-inputs page replacing the diagnostic-entities page) and has one uncommitted whitespace-level edit in `src/content/docs/build/system-prep.md`. Per the sync plan the site must be reviewed and pushed alongside the release. Nothing wrong with the content itself; it just has to be finished.

**F8 — Import summary's completion path carries no "answered" mark (low, code-level gap; real-world impact low).**
Repo: `librecoach-node-red`. `src/tabs/templates/import_summary.js:44-51`.
The 2376059 fix marks the *watchdog* entry `{answered:true}` so late results
are recognized, but the *summary's own* completion path deletes the entry
with no marker. A re-delivered final response after the summary already
answered would re-complete a fresh tally with no entry and attempt a second
HTTP response on the same `res`. Not covered by any test; and the
ha-api/Join pipeline is not expected to re-deliver a response. Node.js
refuses a second write to an ended HTTP response, so worst case is log
noise. A symmetric `{answered:true}` mark on the completion path would close
the last corner. (F9's join caveat is the only thing that would make this
reachable.)

**F9 — Per-response import flush depends on the Node-RED Join passing through `msg.complete` (informational, unverifiable here).**
`8396638`'s design (flush each registry response immediately, tally in
`import_summary`) relies on the join node honoring `msg.complete === true`.
Verified against the project's stated contract and corroborated by the
observed live behavior across three fix commits, but the join source was
unreachable in this read-only environment and no unit test exercises
Join/Split/ha-api (everything downstream of Split is simulated
message-by-message). If a future node-red changed join behavior, the failure
degrades to count-buffering: hangs capped at 30 s by the watchdog, which
would misreport healthy-but-slow imports as "did not report back."

### Known limitation (documented in-tree, not a defect — listed so it is not "fixed" backwards)

**L1 — Sticky diagnostic category on digital inputs.**
An input entity first published *unidentified* carries `entity_category: "diagnostic"`; after the module is identified, the entity re-publishes its name/device with the key **omitted** (correct — HA rejects an explicit null), but HA's registry will not clear a previously-set category on re-discovery. The entity stays diagnostic until a delete+recreate via the Delete HA Entity tab. This is now documented in `FUNCTION-RULES.md` and `status_digital_input.js:177-181`. Consequence: freshly-identified inputs may be absent from the AI dashboard prompt (which filters the diagnostic set) until manual re-creation.

### Confirmed but pre-existing (not 1.7.0 regressions — noted for completeness)

**P1 — Beta `version-check` CI job: the "newest entry body" awk also includes all older entries (latent CI bug, both repos).**
`ha-addons-beta .github/workflows/builder.yaml` (added by `933d7c4`, ported from prod where it already lived). `awk '/^### /{n++} n==1'` never resets `n`, so "body" runs to end of file, contradicting its comment ("up to the next ### heading"). Today it passes (1.7.0 has ✨ New and is a minor bump over 1.6.0). It would misfire on a *future* patch release that declares no new features while any older entry has ✨ New (it would falsely demand a minor bump). Not a 1.7.0 issue.

**P2 — Hardcoded MQTT default credentials in the shipped `data/settings.js`.**
`librecoach-node-red/data/settings.js:11-12` sets `MQTT_USER=librecoach`, `MQTT_PASS=One23four`. Unchanged in this window (identical at baseline `4109cfda`), so not a 1.7.0 finding — but worth knowing: the orchestrator's settings.js placeholder injection (`grep REPLACE_MQTT_`) is dead code as long as the canonical file carries real values instead of placeholders; the authoritative path is the `flows_cred.json` decrypt/substitute/re-encrypt, which I verified works (ciphertext decrypts under the `sha256("librecoach")` key to the 5 MQTT-node cred records containing `${MQTT_USER}`/`${MQTT_PASS}` placeholders, which `run.sh` substitutes with the user's actual options at deploy).

**P3 — `vehicle_bridge` publishes `can/timestamped` which nothing in Node-RED subscribes to.**
Identical at the 1.6.0 baseline; reserved topic, unchanged in this window.

**P7 — The import notification's "Open Import Page" link is dead (confirmed bug, pre-existing — NOT a 1.7.0 regression, unchanged in the window).**
Repo: `librecoach-node-red`. `src/tabs/templates/import_notify_url.js:5-6`
(untouched since the v1.2.3-era import feature; byte-identical at baseline
`4109cfda` and HEAD).
The link is `http://homeassistant.local:1880/endpoint/librecoach/import`,
but the import page's http-in URLs are exactly `/librecoach/import`
(GET+POST, verified in the artifact) — **no `/endpoint/` prefix exists
anywhere in the flows or the add-on**, so the link 404s on every
installation. Additionally the host is hardcoded to
`homeassistant.local:1880` — the same class of defect `66eaaef` eliminated
for the *export* links, missed for the import link (which can't simply be
made relative: it points at Node-RED, not HA, so the host must come from
somewhere).
Failure scenario: user triggers an import → "LibreCoach Import" notification
appears → clicks "Open Import Page" → 404. The page is reachable only by
hand-typing `http://<ha-host>:1880/librecoach/import`.
Why it matters for 1.7.0: the release notes advertise the export-link fix
while shipping a known-dead import link in the same feature. Minimal correct
fix: drop the `/endpoint/` segment (the host part is a deliberate limitation
of serving Node-RED URLs from HA notifications — document it). Confirmed by
artifact http-in URL enumeration + file history; no live click possible
(read-only).

### Confirmed process findings (all resolved before the release point — listed for the inventory)

**P4 — Stale-artifact window from lumpy splitter write-backs (historical, resolved).**
Between `c1b49be` and `82f8379`, several commits (`302f22e`, `fb4eeba`,
`14b302a`) touched only the `.js` split sources, leaving the committed
`artifact/flows.json` behind; `82f8379`'s write-back caught everything up.

**P5 — `4d855ad` contains a commit whose test suite fails at that commit
(historical, resolved).** The digital-input stubs + full test suite were

**P6 — `b186a2d` shipped a NUL byte in a deployed function file (historical,

not even surface (the test file failed to load the source). The

via empty-stub tests today.

### Suspected (not fully confirmable without a live system)

**S1 — Bash version semantics of the `API_TIMEOUT=` prefix (informational).**
`ha-addons-beta librecoach/run.sh` `install_addon`: `API_TIMEOUT=$API_TIMEOUT_IMAGE_PULL api_call ...`. In bash ≤ 5.1 a variable assignment preceding a *function* call leaks into the shell for the rest of the run (every later `api_call` would then use the 1800 s timeout instead of 30 s). In bash 5.2 (verified by experiment; HA's 2026.08 base image is Debian 12 / bash 5.2) it reverts after the call, which is what the code assumes. The shipping base makes this safe; if the base ever moves to an older-bash distro, the 10-minute MQTT-check window could stall on a hung API response. No action needed for 1.7.0.

## Fix-chain re-audit (fixes of earlier releases / in-window fixes of fixes)

**A1 — ATS silence (1.6.0-era feature hardened in this window).**
Chain: `c1b49be` (zero entities when silent) → `302f22e` (mark unavailable).
Original defect: a silent transfer switch left retained MQTT states holding
the last live values (e.g. 118 V / 2100 W) while the coach was dark.
- `c1b49be`'s fix (publish zeros + "No Source Active") had two problems that
  `302f22e` addresses: (a) it *fabricated* a reading — per FUNCTION-RULES.md,
  "unavailable is correct when a device is offline", and the spec only supports
  zero for the AGS voltage criterion, not for source/fault state; (b) the RBE
  bypass stamped `Date.now()`, which collides when two frames land in the same
  millisecond, letting a wake frame be dropped and leaving the zeros on the
  entity.
- At HEAD the defect is genuinely closed: silence >10 s (30 s startup grace)
  publishes a single retained `offline` to the per-instance availability topic
  the entity's discovery references (`availability_mode: all`, so the unit
  going silent takes the entities unavailable while states keep their last
  values); any frame flips it back online and republishes live values; the
  wake-frame case is handled by a monotonic stamp; no default instance is
  invented for coaches without a switch; both nodes publish through the
  *retained* MQTT-out link (terminal mqtt-out node `cacf35b859af22a9`,
  `retain:"true"` in the artifact — no re-subscribe blip can mask the
  offline state), and the monotonic `ats_rbe_stamp`
  (`decode_rvc_can.js:387-405`) keeps a byte-identical wake frame alive
  through the RBE node.
- Same-class sweep: other silent-device classes are handled by their own
  availability paths (geo offline publisher, HVAC unavailable publisher —
  both present and tested in the suite); the new digital-input publisher's
  silence behavior is the open F4 (no per-module watchdog) — the ATS side of
  this exact class got the fix in this window, the TM102 side did not.
- Tests: `test/ats-wake-path.test.js`, `test/ats-watchdog.test.js` — pass in
  the full-suite run (group A: 71/71 across the six ATS/decode/migration/

  response, so the tally never closed and the browser POST hung indefinitely.
  A 30 s per-import watchdog now answers with the partial count
  (`failed += unanswered`, "N entities did not report back").

  **The bug 814991d shipped (what 2376059 fixed) was not a timer race — it
  was bookkeeping ambiguity.** 814991d encoded "the watchdog already
  answered" by *deleting* `importPending[importId]`, and `import_summary`
  discarded any completed tally when the entry was absent (`if (!entry)`).
  Entry absence is ambiguous: it also holds for the ordinary "no pending
  entry in flow context" state — which is exactly the state the two
  pre-existing summary tests run in (empty flow stub), and both assert the
  summary **answers**. So 814991d shipped two deterministically red unit
  tests (its diff touched no test files); 2376059's semantics make them
  green again. (Process finding — see P8.)
- **2376059 — race verdict (independently re-derived, matches the code at
  HEAD).** The answered state is now explicit: the watchdog marks
  `pending[importId] = {answered: true}` instead of deleting it, and
  `import_summary` discards late results only when
  `entry && entry.answered`; no entry at all → answer (the 814991d
  suppression is gone). Walking both orders on the single-threaded
  event loop:
  - Real summary completes first: it reads+deletes the entry and clears the
    timer before answering; the watchdog's own `if (!pending[importId])
    return;` guard then no-ops. One answer.
  - Watchdog fires first: it marks answered and answers; late results build
    a fresh tally (the watchdog deleted the old one), and if they ever
    re-complete it, `entry.answered` discards them. One answer.
  - **The race is closed in both directions** — at most one of the two
    answers, in either order, and a real summary can no longer be
    suppressed. Two known, accepted properties remain: (i) a healthy but
    slow import past 30 s gets a premature partial answer and its accurate
    summary is discarded by design (re-running the import is safe —
    idempotency is tested); (ii) **residual edge, untested**: a
    *re-delivered* final response after the summary's own completion
    re-completes a fresh tally with no entry and answers the browser a
    second time — the summary's completion path carries no
    `{answered:true}` mark (the watchdog's does). Node.js refuses a second
    write to an ended HTTP response, so worst case is log noise; and a
    duplicate websocket response is not something the ha-api pipeline is
    expected to produce. Low severity, noted (F8).
- **Design caveat (F9):** the per-response flush depends on the Node-RED
  Join node passing through `msg.complete === true` — verified only by the
  project's stated contract, not its source (join source unreachable in
  this environment), though the observed live behavior across three
  fix commits corroborates it. If a future node-red changed join behavior,
  the failure mode degrades to count-buffering: hangs capped at 30 s by the
  watchdog, which would misreport healthy-but-slow imports.

## Upgrade impact for 1.6.0 users

1. **Node-RED restarts once** on upgrade (flows hash/version change), as on
   any release. Node-RED revision jumps `4109cfda` → `2376059`.
2. **New entities (additive):** TM102-family digital-input binary sensors
   (named by module + connector pin when identification succeeded) and
   PRODUCT_ID-based device identification (product names in device names,
   stable across firmware; `sw_version` refreshed on firmware change). No
   1.6.0 entity is renamed or removed by these — they attach to
   newly-identified nodes/modules; device identifiers/unique_ids stay
   address-based, so two same-model modules remain distinct devices
   (tested).
3. **Transfer-switch behavior change (the headline fix):** a silent transfer
   switch now makes its entities **unavailable** (last values retained)
   instead of being rewritten to zeros/"No Source Active". Dashboards that
   hard-code numeric handling of `sensor.ats_*` should treat `unavailable`
   as "no source".
4. **Generator start behavior:** dashboard/automation generator starts now
   register a demand (with Manual Override) — a started generator runs until
   an explicit stop command or Quiet Time, instead of being stoppable by the
   AGS's demand poll at any time.
5. **One-time Home Assistant restart** on the first 1.7.0 start **only if**
   `/config/www` did not exist (export directory bootstrap). Harmless but
   user-visible ("HA restarting" in the log).
6. **Orchestrator hardening (invisible in the happy path):** setup now
   disables the self-watchdog at start and re-enables it at the end (1.6.0
   left it untouched mid-setup); API payloads are logged redacted; MQTT
   setup notifications fire immediately when the API confirms, retry on
   failure, and distinguish "HA not answering" from "MQTT not enabled".
   Interrupted Node-RED installs resume instead of prompting; an
   installed-but-never-configured Node-RED is adopted without the takeover
   prompt (F1/F2 are the two edges of that new path).
7. **Entity-map self-healing:** stale discovery records (obsolete Victron
   component types, orphaned map entries) are repaired by the entity-map
   recovery; in rare cases an entity is re-created with a corrected unique_id
   rather than left orphaned (verified: late replays self-heal; an empty
   broker at most misses a cleanup — no live record is ever dropped).
8. **J1939 diagnostics no longer mis-decoded as RV-C** (FECA/FEAE/FEFC) —
   coaches with a SilverLeaf TM102X or other J1939 transmitters will see
   fewer phantom entities and correct RV-C-only diagnostics.
9. **Export/download:** configuration and dashboard exports now work on any
   HA host/port (relative links); exports retain RV details; the import page
   can no longer hang when registry updates go quiet.
10. **No config-option changes, no credential changes, no manual migration
    required.** The preserve-file and context-migration logic is unchanged.
